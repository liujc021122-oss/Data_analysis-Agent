# M19 评测与安全测试设计

## 状态

已获用户确认，准备进入实现计划。

## 背景与目标

现有系统已经具备数据上传校验、结构化模型输出、受限代码执行、证据链报告和资源授权边界，但缺少一个可重复的离线评测入口，无法统一回答以下问题：

- 固定数据和固定问题是否得到正确指标与前三名结果；
- 首次代码执行是否成功，失败后的重试是否受控；
- 图表是否真的生成，报告数字是否与已验证证据一致；
- 空数据、坏编码、重复列名、非法文件、模型协议错误和连续失败是否安全失败；
- 沙箱是否拒绝超时、越权路径和未授权网络；
- 并发任务和不同用户之间是否保持隔离；
- 评测是否可以在没有真实 LLM、网络或 Docker 的 CI 环境完成。

M19 交付一个离线评测套件和一组直接驱动现有安全边界的回归测试。评测套件不改变线上任务编排、数据库模型或执行器安全策略。

## 范围

### 包含

1. `data_analysis_agent.evaluation` 公共模块：固定案例、执行观测、质量指标、阈值和报告汇总。
2. 一个固定的门店销售数据集和预期结果。
3. 使用 Fake LLM 与本地执行器的正常分析流程评测。
4. 覆盖数据、模型、沙箱、报告、并发和权限边界的自动化安全回归测试。
5. JSON 可序列化的评测报告，以及 pytest 运行说明。

### 不包含

- 线上评测 API、数据库表、管理页面或长期结果存储；
- 真实供应商 API、真实外网请求或 Docker daemon 作为 CI 依赖；
- 修改既有安全规则以迁就测试；
- 性能压测、模型质量的统计显著性分析或生产监控替代品。

## 架构

### 评测领域模型

新增 `src/data_analysis_agent/evaluation/models.py`，使用项目现有的 Pydantic 领域模型风格，定义：

- `EvaluationCategory`：`quality`、`data_validation`、`model_protocol`、`sandbox`、`report`、`isolation`、`authorization`；
- `EvaluationCase`：稳定的 `case_id`、描述、问题、数据集标识、预期值和是否属于质量门槛；
- `EvaluationObservation`：任务完成标志、首次代码执行成功标志、重试次数、指标准确率、报告数字一致率、图表成功标志、耗时和估算 Token 成本；
- `EvaluationCaseResult`：案例、观测、通过状态、稳定错误码和安全的失败摘要；
- `EvaluationThresholds`：质量指标的最小值、重试/耗时/成本的最大值；
- `EvaluationMetrics`：汇总后的任务完成率、一次执行成功率、平均重试次数、指标准确率、报告数字一致率、图表成功率、平均耗时和平均 Token 成本；
- `EvaluationReport`：运行 ID、案例结果、汇总指标、阈值和整体通过状态。

模型只允许 JSON 安全的标量、数组和对象；不保存 prompt、完整模型响应、源代码、密钥、本地绝对路径或原始敏感数据。

### 评测运行器

新增 `src/data_analysis_agent/evaluation/runner.py`。运行器通过 `EvaluationAdapter` 协议接收被测系统，职责仅包括：

1. 按稳定顺序执行案例；
2. 将适配器返回的观测校验为 `EvaluationObservation`；
3. 将未预期异常转换为不泄露细节的失败案例；
4. 按质量案例计算指标；
5. 根据阈值生成 `EvaluationReport`；
6. 提供 JSON 序列化结果。

运行器不负责创建 LLM 客户端、不主动访问网络、不读取任意路径，也不改变被测 Agent 的重试策略。真实 Agent、Fake Agent 或其他离线适配器都可以通过协议接入。

## 固定评测数据

固定夹具位于 `tests/fixtures/m19/`：

- `store_sales.csv`：包含多个门店和多条销售记录，足以验证分组求和与前三名排序；
- `store_sales_expected.json`：保存每个门店的销售额、前三名顺序、总额和要求生成的图表类型。

正常案例的问题固定为“计算各门店销售额并找出前三名，同时生成销售额图表和报告”。正常流程使用 Fake LLM 返回确定的分析代码、图表收集动作和最终报告；代码通过现有数据集加载边界读取夹具，图表通过现有输出目录边界写入。评测同时检查：

- 数据集确实被加载且未把本地源路径放入模型提示；
- 执行输出中的门店汇总和前三名与 expected 文件一致；
- 图表文件存在且通过当前任务证据校验；
- 报告中的数字只来自已验证指标，错误数字被标记为待确认。

## 指标定义

只对标记为质量门槛的正常案例计算质量指标。安全负例单独断言“拒绝且不泄露”，不把预期拒绝计入任务完成率。

设质量案例总数为 `N`：

- 任务完成率 = `task_completed=True` 的案例数 / `N`；
- 代码一次执行成功率 = `first_execution_succeeded=True` 的案例数 / `N`；
- 平均重试次数 = 所有案例 `retry_count` 的算术平均；
- 指标准确率 = 所有案例 `metric_accuracy` 的算术平均；
- 报告数字一致率 = 所有案例 `report_numeric_consistency` 的算术平均；
- 图表生成成功率 = `chart_generated=True` 的案例数 / `N`；
- 平均耗时 = 所有案例 `duration_ms` 的算术平均；
- 平均 Token 成本 = 所有案例 `token_cost_usd` 的算术平均。

默认阈值要求任务完成、一次执行、指标、报告数字和图表成功率均为 `1.0`，平均重试次数为 `0.0`。耗时和 Token 成本阈值可选，由调用方按环境配置，不在不同机器上硬编码绝对时间目标。

## 测试矩阵

### 数据校验

通过 `CsvInspector`/`DatasetUploadService` 测试正常 CSV、空文件、只有表头的空数据、包含缺失值的合法数据、无法识别编码、重复列名、超过配置大小的文件和非法扩展名。断言稳定错误码、无对象残留和无元数据残留。

### 模型协议

通过 Fake Provider 驱动非法 JSON、schema 校验失败和连续失败，断言最多进行既定的结构化纠正尝试，最终返回稳定的 `LLMStructuredOutputError` 或供应商错误，不执行未校验的模型内容。

### 沙箱与工具安全

通过 `FakeRuntime` 和注入的执行后端测试超时、输出/资源限制、输入路径越权、输出目录越界、清理顺序和错误消息脱敏。通过 `ToolExecutor` 测试网络未授权、缺少权限、任务上下文不匹配和高风险工具拒绝；网络允许必须是显式策略。

### 报告一致性

通过 `EvidenceRegistry` 注册并复算指标，再由 `ReportService` 生成报告。正确数字必须保留，未验证或错误数字必须进入待确认状态，跨任务图表和越界路径不能成为报告证据。

### 并发与权限

并发运行两个不同任务，断言任务 ID、输出目录、图表和报告互不覆盖。通过 `AuthorizationService`、数据集 resolver 和已有 API 认证夹具断言普通用户不能读取或下载他人资源，管理员行为符合现有审计规则。

## 数据流

```text
固定夹具/固定问题
        |
        v
离线适配器 ---> 现有 Agent/上传/执行/报告边界
        |
        v
EvaluationObservation
        |
        v
EvaluationRunner ---> EvaluationMetrics ---> EvaluationReport(JSON)
```

安全负例不经过质量指标汇总，而是由对应模块的回归测试直接断言稳定错误码、资源清理、隔离和信息脱敏。

## 验收标准

- `pytest tests/evaluation -q` 在无真实 API、网络和 Docker 的环境通过；
- `pytest -q` 通过且既有测试行为不回归；
- 固定门店销售数据可重复运行，输出前三名、图表和报告数字有确定断言；
- `EvaluationReport` 能计算并序列化全部八项质量指标；
- 数据、模型、沙箱、报告、并发和权限测试均有明确自动化覆盖；
- 重要失败路径不泄露本地路径、密钥、源代码和未清洗的内部异常。
