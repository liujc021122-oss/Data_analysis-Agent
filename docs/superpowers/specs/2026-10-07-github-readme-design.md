# GitHub README 与提交材料设计

## 背景

当前仓库已从早期的单体 Python 脚本演进为一个包含前端、API、后台 Worker、持久化、对象存储、报告渲染和受限执行边界的数据分析平台。现有 README 同时混合早期目录、兼容入口和后续 M08-M20 功能说明，不能准确地向 GitHub 访客传达当前架构，也没有稳定的最终报告和图表展示资产。

本次工作只处理公开项目文档和提交准备，不改变业务代码、数据库模型、部署逻辑或测试行为。

## 目标与非目标

### 目标

1. 用当前实现重写根目录 `README.md`，采用中文正文、英文摘要，并保留命令/API/配置变量的官方英文名称。
2. 用 Mermaid 和简洁的仓库树说明前端、API、Worker、数据层、LLM、存储和执行沙箱之间的关系。
3. 明确本地 Python/SQLite、API + Worker 和 Docker Compose 三种启动边界，避免把可选依赖写成必选步骤。
4. 纳入脱敏、可复现的报告展示图和图表展示图，并保证 GitHub 相对链接可用。
5. 新增 `docs/GITHUB_SUBMISSION_CHECKLIST.md`，指导用户安全地选择文件、验证、提交和推送，避免把 `.env` 或现有无关改动带入 commit。

### 非目标

- 不引入 GitHub Actions、自动发布、徽章服务或新的 CI 逻辑。
- 不修改现有未提交的业务代码和测试改动。
- 不伪造未实际运行的测试数字，不把 PDF 或具体 MCP transport 写成已交付能力。
- 不上传真实 API key、数据库密码、签名密钥、宿主绝对路径或敏感数据。

## 方案选择

### 方案 A：单文件 README

只修改 README，把架构、截图和提交命令全部放在同一文件中。改动最小，但截图和提交规范难以独立复用，README 会继续膨胀。

### 方案 B：README + 展示资产 + 提交清单（采用）

README 聚焦项目定位、架构、使用和验证；展示图存放于 `docs/images/`；提交流程单独放到 `docs/GITHUB_SUBMISSION_CHECKLIST.md`。边界清晰，适合当前已经有多种部署方式且后续仍会演进的仓库。

### 方案 C：README + 展示资产 + CI/发布自动化

在方案 B 上增加 GitHub Actions 和自动发布文档。它适合已经确定远程仓库、Secrets 和分支策略的项目，但超出本次“准备第一次上传”的范围，也会引入新的验证和维护成本。

## 信息架构

README 按以下顺序组织：

1. 项目标题、英文摘要、技术栈和当前能力概览。
2. 报告与图表展示图，先让访客看到真实输出。
3. 核心特性：自然语言分析、阶段编排、证据链、报告格式、异步任务、数据隔离和生产执行边界。
4. 系统架构 Mermaid 图和任务生命周期 Mermaid 图。
5. 关键目录结构，使用当前源码路径，不再把早期 `utils/` 单体树当作主架构。
6. 快速开始：安装、环境文件、离线测试和最小 Python/API 启动路径。
7. Docker Compose 部署链接和关键访问地址。
8. 报告输出、证据校验和执行安全说明。
9. 测试分层、验证命令和明确的当前限制。
10. GitHub 上传/提交清单链接、贡献方式和许可证。

README 中的所有状态数字必须来自本轮实际运行或仓库已有、可追溯的验证记录；无法在本轮复核的数字只描述验证命令，不写成结果断言。

## 展示资产

新增以下文件：

- `docs/images/report-preview.png`：脱敏的报告页面/报告内容截图，展示标题、摘要、指标、结论和图表嵌入效果。
- `docs/images/chart-preview.png`：脱敏的分析图表截图，展示真实可读的坐标、标题、图例和数据趋势。

优先使用当前项目生成的结果；若运行时无法生成真实 LLM 结果，则使用项目测试夹具或离线报告服务生成明确标注为示例的结果，不调用真实外部 API，不在图片中出现密钥和用户信息。

## 提交流程

`docs/GITHUB_SUBMISSION_CHECKLIST.md` 包含：

- 检查当前分支和工作区，识别用户已有改动。
- 检查 `.env`、数据库、输出目录、密钥和临时文件是否被忽略。
- 运行与本次文档相关的 Markdown/链接/资产检查，以及项目已有后端/前端验证命令。
- 使用显式路径执行 `git add README.md docs/images/... docs/GITHUB_SUBMISSION_CHECKLIST.md`。
- 使用 `git diff --cached` 和 `git diff --cached --check` 复核 staged 内容。
- 配置或检查 `git remote -v`，再执行 `git commit` 和 `git push -u origin <branch>`。
- 首次推送前提醒用户把 `<owner>/<repo>`、分支名和提交邮箱替换为真实值，并说明本任务不会代替用户执行远程推送。

## 验收标准

- README 不再把过时的单体目录描述为当前主架构。
- README 中的所有内部链接都指向存在的文件；两张展示图片在仓库根目录下可解析。
- README 同时说明兼容 API 和当前 Web/API/Worker/Compose 使用方式。
- 截图为 PNG、可在 GitHub 正常显示，且不包含敏感配置或真实密钥。
- 提交清单明确使用显式 `git add`，不会要求用户执行无差别 `git add .`。
- 本次变更的 `git diff --check` 和 Markdown/资产检查通过；其他工作区改动不被加入本次 staged 文件。
